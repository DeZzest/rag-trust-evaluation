# Ізольована індексація versioned corpus snapshot (пакет 13)

**Стан:** реалізовано окремий індексатор з обов'язковою офлайновою перевіркою; результати на реальному університетському корпусі та інтеграційні тести Ollama/ChromaDB ще не отримано.

## Передумови

- Завершити **фактичне** ручне приймання всіх включених OCR-сторінок та перевірку редакцій нормативних документів.
- Мати вже зібраний `data/corpus_snapshots/<label>/` з `snapshot_manifest.json` і `ingested_corpus.jsonl`, створений пакетом 12.
- Для реальної індексації потрібні запущені Ollama з `EMBEDDING_MODEL` і ChromaDB v2 з налаштованими `OLLAMA_BASE_URL`, `CHROMA_BASE_URL`. Використовується наявний embedding-контракт і REST API репозиторію.
- Для офлайнової перевірки потрібні Node/npm, Python та залежності Node; не потрібні Ollama/ChromaDB.

## Крок 1. Перевірити локальний snapshot без мережевих викликів

```bash
npm run corpus:verify -- --snapshot-dir data/corpus_snapshots/reviewed-ocr-v1
```

Запишіть **точний** `corpusSnapshotId` із результату (формат `sha256:<64 hex>`). Якщо перевірка не проходить, **нічого не індексувати**.

## Крок 2. Dry-run індексації (типова, безпечна поведінка)

```bash
npm run corpus:index-snapshot -- \
  --snapshot-dir data/corpus_snapshots/reviewed-ocr-v1 \
  --expected-snapshot sha256:PASTE_EXACT_64_HEX_ID
```

Приклад `PASTE_EXACT_64_HEX_ID` — placeholder, не реальний хеш. Команда викликає офлайновий `verify_reviewed_snapshot.py`, звіряє SHA-256 JSONL, `corpusSnapshotId`, `chunkId`, кількість фрагментів та метадані. Вона виводить майбутнє ім'я колекції `rag_snapshot_<64hex>`. **Без `--execute` вона не викликає Ollama або ChromaDB**, не генерує embeddings і не створює колекцію.

## Крок 3. Явно дозволити індексацію в НОВУ колекцію

Лише після схвалення snapshot і перевірки необхідних сервісів:

```bash
npm run corpus:index-snapshot -- \
  --snapshot-dir data/corpus_snapshots/reviewed-ocr-v1 \
  --expected-snapshot sha256:PASTE_EXACT_64_HEX_ID \
  --execute
```

Якщо snapshot містить **не всі PDF** із вихідного `scrape_manifest.json`, додатково потрібен прапорець `--allow-partial`. Це окреме, усвідомлене погодження роботи з частковою вибіркою, а не визнання її репрезентативності.

Ім'я нової колекції жорстко обчислюється з `corpusSnapshotId`. Вибрати довільну колекцію, поточну `CHROMA_COLLECTION` або ім'я `lute_university_docs` не можна. Нова колекція створюється з `get_or_create:false`: якщо така вже існує, інструмент **відмовляється використовувати чи дозаписувати** її. Старі `npm run index:corpus`, `retrieve` та API /rag/query залишаються незмінними.

## Контроль помилок

- Валідація і формування плану завершуються **до мережевих викликів**. Пошкоджений JSONL/маніфест, неправильний ID, повторений `chunkId`, не підтверджене джерело — відмова.
- Всі embeddings обчислюються **до створення** нової колекції; порожні/некінцеві або різновимірні вектори — відмова без Chroma-запису. Це збільшує вимоги до RAM на великих корпусах.
- Фрагменти додаються пакетами по 16 і звіряється їхня загальна кількість у Chroma. Перевірка кількості **не доводить** правильність усіх векторів або фактологічну якість retrieval.
- При помилці **після створення колекції** можливе часткове завантаження. Інструмент не видаляє колекцію автоматично і виводить попередження про непридатність до використання. Повторне виконання на тому самому snapshot не змінює колекцію; потрібно провести ручний аудит та окремо вирішити долю часткових даних.
- Імена колекцій зараз жорстко пов'язані з snapshot, а не з embedding-моделлю. **Порівняння різних embedding-моделей на тому самому snapshot вимагає окремого керування конфігураціями/колекціями** у наступних експериментальних пакетах.

## Наукова межа й відтворюваність

Збережіть у журналі експерименту хеш snapshot, `EMBEDDING_MODEL`, версії Ollama/ChromaDB та параметри embedding, дату запуску й фактичну кількість записів. Позитивна перевірка коду/CI без локального середовища **не доводить** завершення переіндексації. Поки не створено експертного gold dataset, не стверджувати про приріст достовірності, зменшення галюцинацій або статистичну значущість нових методів.

Підключення нового `collectionId` до RAG API та запуск на реальних запитах — **окрема контрольована зміна** після перевірки результату індексації.

## Тести

```bash
npm run test:snapshot-index
```

Вони працюють на **синтетичних** фікстурах і підмінних залежностях; перевіряють dry-run без жодних викликів, блокування часткового snapshot, повний pre-embedding, збої, часткові записи та детерміновану назву колекції. Вони не звертаються до реальних Ollama або ChromaDB.
