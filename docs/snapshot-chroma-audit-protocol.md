# Протокол повного read-only аудиту ChromaDB-корпусу (пакет 15)

**Стан:** засіб технічної верифікації всіх індексованих фрагментів, без змін у Trust Score, генерації, OCR або самій ChromaDB.

## Проблема

Відповідність кількості ChromaDB-записів `chunkCount` у `corpus-snapshot/1` і перевірка метаданих лише тих фрагментів, які повернув retrieval, **не доводять цілісності решти колекції**. При тій самій кількості записів можливі підміна тексту, чужий chunkId, неправильна редакція PDF або перекручення метаданих.

ChromaDB v2 підтримує read-only `POST /api/v2/tenants/{tenant}/databases/{database}/collections/{collection_id}/get` з `limit`, `offset` і `include: ["documents","metadatas","embeddings"]`. Цей endpoint використовується **лише для читання**, жодних змін індексу не відбувається.

## Передумови

- Пройшла фактична ручна перевірка OCR-сторінок і документація редакцій; виконано `corpus:snapshot`, `corpus:verify` та `corpus:index-snapshot --execute` із пакетів 12–13.
- У локальному середовищі доступні Node/npm, Python і ChromaDB v2. **Ollama для аудиту не потрібна.**
- Уважно перевірте `corpusSnapshotId` у `snapshot_manifest.json`, а також наявність **саме нової** колекції `rag_snapshot_<64hex>`. Не підставляйте ID зі старого `lute_university_docs`.

## Команда

```bash
npm run corpus:audit-index -- \
  --snapshot-dir data/corpus_snapshots/reviewed-ocr-v1 \
  --expected-snapshot sha256:REPLACE_WITH_ACTUAL_64_LOWERCASE_HEX
```

Запис `REPLACE_WITH_ACTUAL_64_LOWERCASE_HEX` — умовний, не справжній digest. Підставити ID, отриманий `corpus:verify`. Перед першим HTTP-запитом інструмент повторює Python-верифікацію локального snapshot та контроль ID/SHA-256.

Перевірка читає **всю** колекцію порціями по 50 записів і порівнює з локальним JSONL:

1. Точний набір `chunkId` без зайвих чи пропущених ID.
2. Побайтово однаковий у JSON текст кожного chunk (без автоматичної нормалізації).
3. Усі метадані `corpusSnapshotId`, `documentVersion`, `pageNumber`, `sourcePdfSha256`, `reviewedTextSha256` та решта ключів мають **точно збігатися**, включно з типами значень.
4. Всі embeddings існують, містять лише скінченні числа і мають однакову додатну розмірність.
5. Загальний count ChromaDB перевіряється до й після проходу. При будь-якій невідповідності CLI завершується з ненульовим кодом; журнал не називає перевірку успішною.

Звіт `snapshot-chroma-audit/1` містить ID snapshot/колекції, очікувану, фактичну й перевірену кількість записів, розмірність векторів та прапорець `embeddingModelVerified:false`. Тексти університетських документів **не копіюються в stdout**. Сам read-only аудит не створює, не змінює, не очищає й не видаляє жодної колекції.

## Наукові та технічні обмеження

- Скінченність, кількість та розмірність embedding-векторів **не** доводять, що вони створені правильною моделлю, потрібною версією або з правильного тексту. `embeddingModelVerified:false` — принципово важливе обмеження. Наступний пакет має ввести обов'язкове прив'язування та перевірку embedding identity (модель, digest/версія, конфігурація) до індексації й RAG-запиту.
- Точний збіг ID, текстів та метаданих **не** доводить автентичності людської перевірки, нормативної чинності документів, семантичної релевантності чи якості відповіді RAG.
- При одночасній зміні колекції між сторінками аудит не гарантує транзакційний snapshot. Перевіряти треба на «замороженій» колекції, не допускаючи сторонніх записів/видалень під час аудиту.
- Тести CI — **лише синтетичні**, не реальна перевірка Chroma/Ollama.

## Критерії приймання

`npm run test:snapshot-audit` має перевіряти повне сканування 53 елементів двома сторінками, зміну порядку без впливу на результат, підміну документа, фальшиві й дубльовані ID, змінені метадані, вектор із NaN, нульову/неузгоджену розмірність, count mismatch, неповну відповідь Chroma та заборону починати мережевий аудит при недостовірному snapshot.

Зелений GitHub Actions підтверджує тільки програмні інваріанти; кінцеве операційне приймання потребує повного локального запуску на справжній ChromaDB з перевіреним корпусом.
