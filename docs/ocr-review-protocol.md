# Протокол ручного підтвердження OCR та контрольованого експорту (пакет 11)

**Статус:** інструмент для роботи з реально перевіреними текстами; це не автоматична перевірка OCR або чинності нормативного акта.  
**Вхід:** посторінковий `ocr-page-candidates/1` із пакета 10, вихідний PDF, окремий файл ручних рішень `ocr-page-review/1`.

## Чому потрібна ручна перевірка

Посторінкове OCR може спотворити цифри, дату, «не», назви положень і таблиці. `rawOcrMeanWordConfidence` є технічним показником Tesseract і **не доводить** правильності розпізнавання. Відновлення текстового шару не означає чинності редакції. Під час перевірки експерт має відкривати сторінку оригінального PDF, звіряти з нею OCR і вручну виправляти помилки.

## Покрокове виконання

1. Виконати **повний** OCR одного документа. `--max-pages 1` є лише smoke test і **не** придатний для експорту.
2. Сформувати *незаповнений* аркуш перевірки без жодних автоматичних рішень:

```bash
npm run ocr:review-template -- \
  --staging data/ocr_staging/lute_regulations_2026_pdf_8.ocr.json \
  --output data/ocr_review/lute_regulations_2026_pdf_8.review.json
```

3. Перевірити **всі сторінки** за вихідним PDF і заповнити аркуш. Поля `documentVersion`, `verifiedDocumentYear`, `versionEvidenceNote`, `versionReviewerId`, `category` не можуть автоматично братися зі `declaredSourceYear` або назви файла. Вказати фактичні джерела перевірки редакції; `verifiedDocumentYear` означає рік перевіреної редакції, **не** доказ чинності станом на поточну дату.
4. Для кожної сторінки необхідні `pageNumber`, `candidateTextSha256`, `decision`, `reviewerId`, `reviewedAt` (ISO 8601 із часовим поясом), `reviewNote`:
   - `decision: "approved"`: явно вказати `reviewedText` після візуальної звірки, навіть якщо текст не потребував виправлень.
   - `decision: "excluded"`: видалити поле `reviewedText` і пояснити причину виключення. Відсутні/незрозумілі сторінки не можна тихо пропускати. Якщо весь документ виключено — експорт заборонений.
   - `pending` або неповне рішення не проходить перевірку.
5. Лише після фактичної перевірки виконати:

```bash
npm run ocr:review-export -- \
  --staging data/ocr_staging/lute_regulations_2026_pdf_8.ocr.json \
  --review data/ocr_review/lute_regulations_2026_pdf_8.review.json \
  --pdf data/raw_pdf/ORIGINAL_CACHED_FILENAME.pdf \
  --output-dir data/university_corpus_ocr_lute_regulations_v1
```

Підставити **фактичне ім'я** PDF із `data/raw_pdf/`. Назва вихідного каталогу повинна починатися з `university_corpus_ocr_`, бути **новою**, інакше команда відмовиться писати файли. Один виклик експортує **один документ**; об'єднання перевірених документів у цілісний корпус — наступний пакет, який включатиме зміну ingest-пайплайну.

## Формат review

Файл `ocr-page-review/1` має `documentId`, `sourcePdfSha256`, `stagingSha256`, `documentVersion`, `verifiedDocumentYear`, `versionEvidenceNote`, `versionReviewerId`, `category`, `pages`. Усі хеші потрібно перенести без змін із pending worksheet. Номер, хеш і рішення мають відповідати **кожній** сторінці `staging`.

Невелика ілюстрація **синтетичних** полів одного рішення (не справжня розмітка університетського документа):

```json
{
  "pageNumber": 1,
  "candidateTextSha256": "<sha256 from staging page 1>",
  "decision": "approved",
  "reviewerId": "reviewer-identifier",
  "reviewedAt": "2026-11-18T14:30:00+02:00",
  "reviewNote": "Звірено дату і формулювання за оригінальним PDF",
  "reviewedText": "Умовний текст, особисто перевірений на зображенні сторінки."
}
```

Цей приклад **не готовий файл** і не має реального `candidateTextSha256`. Повноцінний шаблон генерує `ocr:review-template` з явним `pending` на кожній сторінці.

## Результати та походження

Команда `ocr:review-export` перевіряє SHA-256 точних байтів `staging`, вихідного PDF, тексту кожної OCR-сторінки й review-файла. Експортуються `<documentId>.txt` у структурі `Document:/Source:/Year:/Category:/URL:/ScrapedAt:/Section/` для подальшого ingest, а також `<documentId>.provenance.json`.

- `Year:` у вихідному TXT походить виключно з ручного поля `verifiedDocumentYear`; можливі помилки перевіряльника програма виявити не здатна.
- Фізичні сторінки PDF зберігаються як `Section N. PDF-сторінка N`. Вхідний `reviewedText` без змін зберігається у provenance, тоді як TXT містить chunked-версію для пошуку.
- Відхилені сторінки залишаються в provenance з причиною, але не входять до індексованого TXT.
- Підпис рецензента та достовірність його візуальної перевірки є організаційними, не криптографічними гарантіями.

## Вимоги до приймання та наступні дії

**До індексації заборонено:** зливати кандидатний staging без review, підміняти вихідний `data/university_corpus/` чи старий `data/ingested_corpus.jsonl`.

Після перевірки усіх документів потрібно окремо: зібрати повний версійний корпус, вибірково перевірити експорт за сторінками, ввести `--corpus-dir`/окремий JSONL з контрольованим `corpusSnapshotId` для `ingest:corpus`, переіндексувати ChromaDB, створити нову чергу експертної розмітки та виконати фактичні експерименти. Без цього немає підстав оголошувати поліпшення Trust Score.

## Автоматична перевірка коду

```bash
npm run test:ocr
```

Використовуються **вигадані** приклади; перевіряються інваріанти файлів, хешів, рішення для кожної сторінки, невідповідність PDF, повнота і неможливість перезапису. Це **не** вимірювання точності українського OCR і не підтвердження чинності університетських положень.
