# Протокол мінімального експерименту: baseline vs claim-aware Trust Score (пакет 17)

**Призначення:** фінальний невеликий програмний метод для порівняльного дослідження. Після прийняття цього пакета діє **feature freeze**, за винятком помилок, що блокують мінімальне ТЗ.

## 1. Методи та формули

### Baseline (наявний `trust.score`)

Стандартний `processRagQuery` використовує lightweight-метод:

```text
S_baseline = 0.60 * RetrievalQuality
           + 0.25 * CitationCoverage
           + 0.15 * CitationValidity
```

Показники нормалізовані до [0;1]; за неусунених помилок посилань після retry score обмежується 0.35. Це показник технічної релевантності й формальної коректності цитування, **не семантичної істинності**.

### Candidate (новий `trust.claimAware.score`)

Якщо `includeClaimGrounding: true`, на **тій самій відповіді** окремий LLM-суддя розбиває відповідь на атомарні твердження й пропонує verdict `supported`, `contradicted`, `unsupported` або `uncertain`.

```text
supportFraction = count(supported) / count(all classified claims)
S_uncapped      = 0.65 * S_baseline + 0.35 * supportFraction

S_candidate = S_uncapped

якщо є хоча б одне contradicted: S_candidate = min(S_candidate, 0.25)
якщо є хоча б одне unsupported:  S_candidate = min(S_candidate, 0.50)
якщо є хоча б одне uncertain:    S_candidate = min(S_candidate, 0.70)
```

При кількох категоріях діє найсуворіший cap. Ці коефіцієнти — **початкова дослідницька гіпотеза**; вони зафіксовані до експерименту, а не підігнані під тестовий набір. Не інтерпретувати `S_candidate` як калібровану ймовірність достовірності.

Коли LLM-суддя не відповідає або не повернув жодного коректно класифікованого твердження, `trust.claimAware.status="unavailable"` та `trust.claimAware.score=null`. Не підміняти їх нульовим значенням або середнім балом. Baseline залишається окремим.

## 2. Як викликати

Сервіс Ollama і ChromaDB мають бути запущені, а реальний snapshot — перевірений і погоджений за попередніми пакетами. Для захищеного дослідницького варіанта:

```http
POST /rag/query/snapshot
Content-Type: application/json

{
  "query": "Які вимоги наведено в конкретному положенні?",
  "topK": 3,
  "includeClaimGrounding": true
}
```

Дослідницька відповідь містить `trust.score` — **старий baseline**, та `trust.claimAware` — **новий результат**. У новому breakdown є `baselineScore`, `score` або `null`, `counts`, `totalClaims`, `supportedFraction`, `uncappedScore`, `capReasons`, `capValue`, `issue`, `methodId="claim-aware-v1"`. Також повертаються `claimGrounding.claims`, цитовані фрагменти, метадані документа/сторінки, `corpusSnapshotId`. Поле `trust.score` **не перезаписується** експериментальним методом.

За відсутності `includeClaimGrounding:true` існує лише baseline без додаткового запиту до LLM-судді.

## 3. Протокол реального порівняння

1. Обрати обґрунтований, перевірений за PDF **підкорпус**, не вимагаючи OCR усіх сканів; записати `corpusSnapshotId`, `EMBEDDING_MODEL`, генеративну/оціночну модель, `topK`, конфігурацію запиту.
2. Підготувати **20–30 реальних українськомовних запитів** із різними типами питань, зокрема невідомі факти й суперечності. Це орієнтир мінімального дослідження, а не уже виконаний benchmark.
3. За чинним протоколом анотацій отримати незалежні оцінки двох людей і арбітраж там, де це потрібно; створити gold **без використання виходу оцінюваного LLM як правди**.
4. Запустити однакові RAG-запити на одному snapshot з `includeClaimGrounding:true`. Для кожного випадку зберегти вихідний JSON з `query`, відповіддю, фрагментами, обома score, суддівськими verdict, конфігурацією і статусом помилки.
5. Окремо скорити **зіставлені за caseId/claimId** прогнозні verdict проти gold за `benchmark:score` (автоматичне вирівнювання довільних тверджень відсутнє). Можна порівняти descriptive-дистрибуції scores та фіксувати ситуації, коли новий метод штрафує реальні суперечності, а baseline — ні.
6. `dev` використовувати для обговорення порогів; `test` — тільки для фінального оцінювання. Якщо рівень розмітки не підтримує кількісне порівняння двох scores, **не заявляти про вищу точність** і чесно обмежити висновки якісним аналізом.

Не приховувати випадки `status:unavailable`, `score:null`, відсутність джерел або помилкові відповіді. Не порівнювати `gold_claim_classification` з `aligned_rag_claims` як одну й ту саму метрику.

## 4. Наукові обмеження

- Твердження `supported` і `contradicted` — **LLM-прогнози**, не експертно доведені мітки.
- Перевірка `evidenceQuote` підтверджує **наявність підрядка**, не логічний зв'язок між цитатою і твердженням.
- LLM може пропустити твердження, розбити одне на кілька чи помилково позначити суперечність. Формула не виправляє цих помилок.
- Можливе `S_candidate < S_baseline` без реального підвищення якості виявлення недостовірності; треба перевіряти **узгодженість із gold**, а не просто менший/більший бал.
- Синтетичні тести перевіряють математичні інваріанти (cap, null, арифметика), не є емпіричними даними й не доводять переваги методу.

## 5. Feature freeze після пакета 17

Після Merge: **жодних нових архітектурних підсистем**. Етапи №18–20 присвячені реальному корпусу, gold-розмітці, інтеграційному запуску, оцінкам і написанню магістерської роботи. Дозволені лише виправлення, необхідні для виконання погодженого мінімального ТЗ.
