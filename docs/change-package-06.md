# Пакет 6 — незалежна експертна розмітка та погодження

**База:** `main` @ `4e7f83e55c86bd4cd0cb430035628fd606e703ce` (merged PR #19)  
**Робоча гілка:** `feat/annotation-adjudication`  
**Статус:** план впровадження, не фінально затверджене ТЗ.

## Мета

Створити формальний міст між чергою кандидатних джерел (`annotation-queue/1`) і еталонним набором (`GoldBenchmark 1.0`). До цього моменту немає перевірки первинних рішень двох незалежних анотаторів, їхніх розбіжностей або обов'язкового арбітражу.

## Файли / зміни

1. `src/modules/evaluation/annotation.review.ts`: схема `annotation-review/1` для вручну підготовлених атомарних тверджень, двох первинних анотацій на кожне твердження, **явного** рішення арбітра та пояснення; перевірка відповіді й посилань до `annotation-queue/1`, точного тексту й ідентифікатора фрагментів, документальних версій і цитат.
2. `src/modules/evaluation/annotation.agreement.ts`: частка погоджень та коефіцієнт Коена κ для тієї самої пари анотаторів на всіх твердженнях, кількість розбіжностей, розподіл вердиктів. Якщо κ не визначено (очікувана згода дорівнює 1), повертати `null`, а не видавати завищену оцінку.
3. `src/modules/evaluation/annotation.review.cli.ts`: команда `benchmark:adjudicate -- <queue.json> <review.json> [gold-output.json]` для офлайнової перевірки, звіту узгодженості та **опційного** формування gold лише після повного арбітражу. Не перезаписувати файли.
4. `src/tests/annotation.review.checks.ts`: тільки синтетичні фікстури для збігу/розбіжності, невалідного доказу, дубліката, джерела не з черги, неповного рішення, кappa.
5. `package.json`, `data/benchmark/README.md`, `docs/benchmark-annotation-protocol.md`: команди, протокол і межі.
6. Додати перевірки в `test:benchmark` (вже запускається GitHub CI).

## Критерії приймання

- Структура арбітражу неможлива без **двох окремо записаних** суджень і явного погодженого рішення для **кожного** твердження.
- Неправильний `sourceId` або вигадана `evidenceQuote` відхиляються як для анотаторів, так і для арбітра; підтримка і суперечність без доказів неможливі.
- Ідентифікатори й текст джерел мають повністю відповідати черзі, `corpusSnapshotId` також; версія документа заповнюється окремо після людської перевірки.
- Вихідний gold відповідає `validateGoldBenchmark`, зберігаючи всі вердикти арбітражу без вигадування даних.
- Узгодженість розраховується **до арбітражу**; результати не оголошуються емпіричними, поки немає реальних анотацій.
- Unit-тести зелені, TypeScript typecheck і frontend build зелені; `main` не змінювати до прийняття PR.

## Обмеження

Ідентифікатори анотаторів не доводять їхню фактичну незалежність; потрібно застосувати організаційний протокол сліпої розмітки. У цьому MVP одна й та сама пара анотаторів працює над усім набором для коректної агрегованої κ. Не створюється жодного реального експертного рішення, аналіз не порівнює моделей і не змінює Trust Score.
