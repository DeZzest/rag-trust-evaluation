# Пакет 11 — приймання OCR-сторінок і контрольований експорт корпусу

**База:** main @ `46d90d726846bcd1c7095adaf2fcf24307474940` (merged PR #25).  
**Робоча гілка:** `feat/ocr-reviewed-corpus-export`.  
**Статус:** реалізаційний план (не остаточно затверджене повне ТЗ).

## Підстава

OCR staging із пакета 10 формує `ocr-page-candidates/1`: кандидатні тексти PDF-сторінок, хеші, raw word confidences, але не перевіряє точність розпізнавання. Без незалежного ручного рішення текст не можна вважати прийнятим. Поточний `ingest_corpus.ts` читає лише вихідний `data/university_corpus` і може вивести рік із назви файла; `year=2026` для старих PDF не означає фактичну редакцію.

## Заплановані зміни

1. `scripts/ocr_review_export.py`: офлайновий валідатор `ocr-page-review/1`, який приймає staging JSON, **окремий написаний людиною review JSON** і вихідний PDF; звіряє `stagingSha256` (точні байти файла), `sourcePdfSha256` (реальні байти PDF), `documentId` і `pageCount`.
2. Кожна сторінка має рівно одне рішення `approved` або `excluded` із `reviewerId`, ISO timestamp, `reviewNote`, `candidateTextSha256`. Для `approved` потрібен явно наданий `reviewedText`; для `excluded` текст заборонено. Відсутні, зайві чи повторні сторінки, неповний OCR-файл, невірні хеші або суто виключені сторінки блокують експорт.
3. Відомості про редакцію вносяться окремо вручну: `documentVersion`, `verifiedDocumentYear`, `versionEvidenceNote`, `versionReviewerId`; рік із вихідного PDF staging не переноситься як перевірена чинність. За відсутності перевірки редакції експорт заборонено.
4. Експортувати **новий окремий** каталог `data/university_corpus_ocr_...` із структурованим TXT для подальшого ingest і JSON sidecar з точними reviewed texts, page provenance, рішеннями анотаторів, SHA-256 та хешами згенерованих TXT.
5. Жодних мережевих викликів/LLM/автоматичної оцінки якості; жодних змін у вихідних TXT, PDF або `ingested_corpus.jsonl`; не запускати індексацію.
6. Додати синтетичні тести для порожніх/фальсифікованих/неповних review, усіх excluded, хешів і безпечних шляхів; додати до GitHub Actions.
7. Описати ручну перевірку й наступну інтеграцію нової версії корпусу з ingest/index у `docs/ocr-review-protocol.md`.

## Критерії приймання

- `review` неможливо замінити самим staging-файлом або згенерувати з оцінки Tesseract.
- Жоден OCR-текст не експортується без explicit reviewedText та ручного рішення по кожній PDF-сторінці.
- `sourcePdfSha256`, `stagingSha256`, `candidateTextSha256` і SHA-256 експортованого TXT звіряються; вихідні дані не переписуються.
- Фізичні номери PDF-сторінок зберігаються в Section і JSON sidecar; хеші reviewed-сторінок доступні для перевірки.
- `verifiedDocumentYear` не виводиться зі `declaredSourceYear` чи імені файла.
- Передача результату до ChromaDB — **окремий контрольований етап**, після версійної перевірки та повторного інжестування.

## Межі

Пакет не створює «реального» ручного рішення й не доводить точність OCR. Перевірка фактичної незалежності рецензента і чинності нормативних актів залишається позапрограмною процедурою. Немає нових числових результатів із RAG і жодних змін Trust Score.
