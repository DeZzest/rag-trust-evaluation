# Еталонний корпус і протокол розмітки тверджень

**Статус:** протокол v0.1, ще без експертно валідованих прикладів.

## Джерела і контроль якості

- Обирати дозволені для наукового використання університетські нормативні документи з явними датами, редакціями та контрольними хешами корпусу.
- Фіксувати `corpusSnapshotId`, `documentId`, `documentVersion`, `source.id`, джерельний текст.
- Кожний випадок має `query`, `split` (dev/test), перелік `claims` і відтворювані джерела.
- Два незалежні анотатори дають первинні оцінки; суперечки погоджуються. Поля `annotatorIds` і `adjudicatedBy` — метадані; CLI **не перевіряє особу чи фактичну незалежність анотаторів**.
- Не включати персональні дані студентів, закриті накази або документи без прав на використання.

## Чотири вердикти

- `supported`: твердження прямо або логічно підтверджене указаним контекстом, без додаткових припущень.
- `contradicted`: твердження несумісне з інформацією указаного джерела.
- `unsupported`: у заданому retrieved-контексті немає достатнього підтвердження.
- `uncertain`: джерело неоднозначне, часткове або недостатнє для впевненого рішення.

Для перших двох категорій обов'язкові `sourceId` та дослівний `evidenceQuote` (після нормалізації пробілів, мінімум 12 символів). Для двох інших ці поля в схемі заборонені. Наявність цитати доводить лише її текстове походження, але **не доводить правильності вердикту**.

## Розділення наборів і запобігання витоку

- `dev`: вибір промптів, параметрів та прототипування; `test`: фінальна оцінка з зафіксованими налаштуваннями.
- Споріднені версії документа та майже однакові запити не повинні розподілятися між dev/test без спеціального обґрунтування.
- Еталонні claimId слід узгодити вручну. Автоматичний зіставлювач довільно сегментованих тверджень у цьому пакеті не створено.
- При порівнянні вказувати всі невдалі запити, пропущені класи та розміри вибірок.

## Метрики

`benchmark.metrics.ts` обчислює confusion matrix, класові precision/recall/F1, macro-F1 (усі чотири класи), accuracy, кількість пропущених суперечностей і частку таких пропусків. Якщо в gold немає суперечностей, `contradictionMissRate=0` — **технічна конвенція**, не підтвердження якості; треба окремо вказувати support. Дані повинні мати принаймні одну спостережувану мітку кожного класу для повного порівняння.

## Мінімальний формат

Застосовуйте `schemaVersion: "1.0"`, непорожні `datasetId`, `corpusSnapshotId` і масив `cases`. Кожний case включає `id`, `query`, `split`, `annotatorIds` (щонайменше два різних), `adjudicatedBy`, непорожні `sources` та `claims`. Кожне джерело включає `id`, `documentId`, `documentVersion`, `text`. Кожне твердження — `id`, `text`, `verdict` та, де потрібно, доказ.

## Команди

- `npm run benchmark:validate -- path/to/gold.json` — лише валідація JSON.
- `npm run test:benchmark` — **синтетичні** unit-тести, а не результати експериментів.

У репозиторії немає готового еталонного датасету. Після розмітки окремо фіксувати узгодженість експертів та обґрунтування розміру вибірки.

## Підготовка доказових фрагментів перед незалежною анотацією

`benchmark:prepare` зіставляє очікувані назви документів у попередньому файлі `data/eval_queries.json` з фактичними `metadata.documentId` і `metadata.year` локального `data/ingested_corpus.jsonl`. Воно **не вважає** ці попередні reference IDs експертною істиною. Підказка `expectedSourceSection` лише змінює порядок перегляду кандидатів.

Вихідний формат `annotation-queue/1` має `originDatasetId`, `corpusSnapshotId`, `ingestedSha256`, `queriesSha256`, `cases[].candidateSources` та `cases[].missingDocumentIds`. Кожний фрагмент включає `contentSha256`, `documentId`, `declaredYear`, `versionVerified:false`, текст та номер рядка інжестованого корпусу. **Рік метаданих сам по собі не доводить чинності редакції**.

Перш ніж створити справжній gold:
1. Перевірити ліцензію, джерело, редакцію та коректність кожного кандидатного документа. Для відсутніх джерел отримати оригінальний документ або позначити випадок недоступним, не підміняти текст.
2. Анотатори незалежно формують атомарні фактичні твердження українською, за потреби включаючи підтримку, суперечності, відсутність даних та неоднозначності. Наукові приклади не можуть бути скопійовані із синтетичних unit-тестів.
3. Узгодити `claimId`, вердикти, `sourceId` та дослівні `evidenceQuote`. Зафіксувати процедуру вирішення розбіжностей, кількість анотаторів та метрику їхньої згоди.
4. Створити **новий** файл за gold-схемою `schemaVersion: "1.0"`, перевірити через `npm run benchmark:validate -- path/to/gold.json` і не змінювати `test` після калібрування.
5. Повторно зібрати corpus snapshot за тим самим вмістом і SHA-256 для відтворення. Якщо файли змінилися, це нова версія корпусу.

Без цих кроків черга є лише **кандидатними фрагментами для ручної роботи**, а результати Precision/Recall/F1 не можна назвати експериментальними.
