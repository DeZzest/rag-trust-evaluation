# Пакет 13 — ізольована індексація перевіреного snapshot у ChromaDB

**База:** main @ `00e74807f336ea706fafd2b75e6edfceee630aec` (PR #27 merged, push CI Success).  
**Гілка:** `feat/snapshot-isolated-chroma-index`.  
**Статус:** план змін до написання коду; загальне ТЗ магістерської роботи ще не затверджене остаточно.

## Підстава

Пакет 12 формує та перевіряє `corpus-snapshot/1` з фізичними PDF-сторінками, `chunkId` і SHA-256. Старий `npm run index:corpus` читає `data/ingested_corpus.jsonl` і через `getOrCreateCollection` використовує `CHROMA_COLLECTION` або `lute_university_docs`. Це не можна переиспользувати для нових наукових snapshot: є ризик змішування індексів різних редакцій документів.

## План

1. Додати **окремий** CLI `npm run corpus:index-snapshot -- --snapshot-dir <path> --expected-snapshot sha256:<64 hex> [--execute] [--allow-partial]`.
   - Типово `dry-run` (жодного Ollama/Chroma-запиту);
   - перед `--execute` обов'язково вимагати точний snapshot ID, який користувач перевіряє вручну;
   - неповні snapshot не індексувати без явного `--allow-partial`.
2. Перед будь-яким мережевим запитом викликати `scripts/verify_reviewed_snapshot.py` на фактичному каталозі, ще раз звірити SHA-256 JSONL, кількість та унікальність chunkId. При будь-якій помилці — зупинити виконання до запису.
3. Ім'я нової колекції детерміновано `rag_snapshot_<64-hex>`; не дозволяти зміну імені користувачем, не торкатися активної/legacy колекції. Використовувати ChromaDB POST create з `get_or_create:false` та окремою перевіркою, що колекції ще немає. Існуючі колекції не перезаписувати, не очищати й не доповнювати.
4. Попередньо згенерувати і перевірити **всі** embeddings до створення нової колекції; після цього додавати Chroma-записи по 16 і перевіряти остаточну кількість записів. Під час помилки після створення нової колекції НЕ виконувати автоматичного видалення; повідомляти про можливу часткову колекцію для ручного аналізу.
5. У Chroma metadata зберігати `corpusSnapshotId`, `documentVersion`, `pageNumber`, `section`, `subsection`, `chunkId`, `sourcePdfSha256`. Заборонити підстановку вигаданих metadata/ID.
6. Додати лише синтетичні offline unit-тести (validation, fail closed, batch insertion, no-write dry run, partial snapshot gate) і підключити до CI, документувати протокол.
7. **Не змінювати** поточні `index:corpus`, `retrieve`, API /rag/query чи Trust Score. Переключення RAG на нову колекцію — наступний окремий приймальний етап після індексаційної перевірки.

## Критерії завершення

- PR є незалежним від роботи локального Chroma в CI; синтетичні тести зелені.
- Dry-run не робить жодних HTTP-запитів, не генерує embeddings і не змінює жодних файлів.
- Пошкоджений snapshot або невідповідний ID відхиляється до будь-якого мережевого виклику.
- Повторна індексація того самого snapshot не змінює існуючу колекцію.
- При помилках генерації embeddings нова колекція не створюється; при частковому записі фіксується недостовірний стан, без автоматичного «успіху».
- Звіт містить `snapshotId`, `collectionName`, `chunkCount`, перевірену кількість записів у ChromaDB, статус повноти corpus.
- Немає жодної заяви про точність OCR, достовірність відповідей чи наукову перевагу Trust Score до реальних експериментів.
